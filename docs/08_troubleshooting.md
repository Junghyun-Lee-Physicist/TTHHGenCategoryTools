- **T-19** | 2018 `TTbar_SemiLep` 이 제출 직후부터 **하루 동안 아무 job 도 안 돌았다.** `--resubmit` 은 `Status information is unavailable`, `--status` 는 `Status on the CRAB server: SUBMITREFUSED` + `Warning: The splitting on your task generated 10010 jobs. The maximum number of jobs in each task is 10000` (2026-07-27) | **CRAB 는 task 당 job 10,000 개가 하드 상한이다.** 이 MiniAOD 는 **10,010 파일**이고 `units_per_job: 1` 이었으므로 10,010 job → 10 개 초과. 치명적인 점은 **제출 시점에 거부되지 않는다**는 것: client 는 `submitted : 7` 로 성공을 보고하고, **서버가 나중에** task 를 `SUBMITREFUSED` 로 세워 둔다. 그래서 (a) 제출 로그·문서에 "7 tasks / 20,953 jobs 제출됨"이 남았지만 실제로 돈 것은 **6 tasks**, (b) `jobsPerStatus` 가 비어 있어 `--report` 행이 전부 0 → "아직 안 시작"과 구분이 안 되고, (c) `crab resubmit` 은 **scheduler 에 도달한 task 의 FAILED job 만** 재큐하므로 원리적으로 손을 못 쓴다. 20,953 = 188+**10,010**+7,195+3,069+219+169+103 이라 총합만 보면 이상이 안 보였다. | **① 예방**: `--preflight --check-das` 가 이제 DAS 의 `nfiles` 를 읽어 `ceil(nfiles/units_per_job)` 를 계산하고 10,000 초과면 **FAIL**(90% 초과면 WARN), 필요한 `units_per_job` 값까지 알려 준다. **② 수정**: `datasets.yaml` 의 해당 항목에 **`units_per_job: 10`** 을 박았다(→ 1,001 jobs). 항목별 override 는 원래 지원됐다(`build_config()`: `dataset_entry.get("units_per_job", res.get(...))`). 최소 수정은 2(5,005 jobs)지만 10 을 택한 이유: **묶음 단위는 물리에 무관**하고(`matchTtbarId` 가 filelist 전체에 3-key map 하나를 만들 뿐, 어느 파일에서 온 행인지 안 본다), upj=1 은 job 2.4분 중 ~90초가 시작 오버헤드라 CRAB 이 매번 경고하던 `CPU efficiency < 50%`(실측 20~45%, waste 50~58%)의 원인이었다. upj=10 이면 job ~10.7분에 오버헤드 비중 ~14%. 출력 파일도 10,010 → 1,001 개로 줄어 뒤의 `sortSplitExtend`/`matchTtbarIdSorted` 가 싸진다. **단, 이미 완료·진행 중인 6 task 는 건드리지 않았다** — 값을 바꾸려면 kill → project dir 삭제 → EOS 산출물 삭제 → 전량 재생산이라 끝난 일을 버리는 짓이다. 그래서 2018 은 현재 혼합 설정(SemiLep 만 10, 나머지 1)이고 그래도 무해하다. **③ 가시성**: `--report`/`--status` 가 task-level `SUBMITREFUSED`/`SUBMITFAILED`/`FAILED`/`UNKNOWN` 을 `[!! ... !!] this task will NEVER run` 로 크게 찍고, 요약에 DEAD TASK 목록을 낸다. **④ 복구 절차**: SUBMITREFUSED 는 산출물이 없으므로 EOS 청소가 불필요하다 — `rm -rf crab_projects/crab_TTbar_SemiLep_2018_extend` 후 `--process TTbar_SemiLep --era 2018` 로 재제출.
